## Предложенная структура `fuzzy/` (минимум файлов, максимум ясности)

```text
fuzzy/
  __init__.py
  run_stage3.py
  io.py
  core.py
  engine.py
  rules.yml
```

## 1) `fuzzy/run_stage3.py` — точка входа (CLI)

Что делает:

* принимает “один отзыв” (id или текст/строку features) или “батч”
* запускает пайплайн этапа 3
* печатает красивый отчёт в терминал (4 числа + агрегации терм→μ + опционально топ-правила)
* управляет флагами типа `--pretty`, `--top-k`, `--json`, `--out`.

Краткий вывод: один файл, который запускают руками, и он отвечает за UX/терминал.

## 2) `fuzzy/io.py` — ввод/вывод данных

Что делает:

* чтение `features.jsonl` (и выбор одного отзыва по `id`)
* запись `final_metrics.jsonl`
* (опционально) запись `fuzzy_inputs.jsonl` / `debug_report.json` если включён debug.

Краткий вывод: вся “файловая рутина” в одном месте, чтобы `core/engine` были чистыми.

## 3) `fuzzy/core.py` — признаки + термы + фаззификация (без правил)

Что делает:

* считает derived features: `magnitude`, `conflict`, `hedges_rate` (и нормировки)
* хранит определения лингвистических термов (треугольник/трапеция) и функции принадлежности
* выполняет фаззификацию входов → словари `{терм: μ}` для каждого входного признака.

Важно: здесь же фиксируем, что в README в пункте 3.2 мы держим только текстовые термы, без числовых диапазонов (как ты хотел).

Краткий вывод: `core.py` превращает “числа этапа 2” в “μ по термам”, но не принимает решений.

## 4) `fuzzy/engine.py` — правила → агрегация выходов → дефаззификация

Что делает:

* загрузка базы правил из `rules.yml`
* нечёткий вывод (Mamdani или Sugeno — выберем один и зафиксируем)
* агрегация по каждому выходу: `output_name -> {терм: μ}` (то, что ты хочешь печатать в терминал)
* дефаззификация → 4 итоговых числа:

  * `final_tonality_crisp`
  * `trust`
  * `final_emotion_intensity`
  * `impression_strength`
* (опционально) формирование “вклада правил” для блока TOP RULES.

Краткий вывод: вся “логика принятия решения” живёт здесь: от μ-входов до 4 метрик и распределений.

## 5) `fuzzy/rules.yml` — база правил (отдельно от кода)

Зачем YAML:

* редактируется как “конфиг”, без лезвия в Python
* легко версионировать и обсуждать

Что хранит:

* список правил с понятными именами
* условия по входным термам
* заключения по выходным термам
* (опционально) вес правила

Примерно в таком духе (не полный список, просто идея формата):

* `IF score_crisp=позитивная AND coverage=высокое THEN trust=высокое`
* `IF conflict=высокий AND magnitude=высокая THEN impression_strength=высокая`

Краткий вывод: правила — данные, не код; менять/дополнять можно без правок модулей.

## 6) `fuzzy/__init__.py`

Минимально:

* чтобы `fuzzy` был пакетом
* можно экспортировать `run_review()` / `run_batch()` как публичный API.

Краткий вывод: техническая обвязка для импорта.

## Как будет выглядеть поток данных (один отзыв)

* `io.py` читает features по `id`
* `core.py` добавляет derived (`magnitude/conflict/hedges_rate`) и фаззифицирует входы
* `engine.py` прогоняет правила → выдаёт:

  * 4 числа
  * агрегации выходов терм→μ (обязательно)
  * (опционально) топ-правила
* `run_stage3.py` красиво печатает и/или пишет jsonl
