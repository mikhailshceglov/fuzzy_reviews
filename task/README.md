# Декомпозиция задачи

Ниже — разделение всей системы на три крупные части:

1. Офлайн-генерация авто-словаря (нейросетью).
2. NLP-обработка конкретного отзыва.
3. Нечёткая логика (fuzzy-ядро системы).

Каждый блок можно рассматривать как отдельный модуль/подсистему.

---

## 1. Офлайн-генерация авто-словаря (нейросетью)

**Цель:**
Построить *большой, доменно-независимый словарь* лемм с оценочной полярностью `polarity(w) ∈ [−1; 1]`, не выписывая его руками.

**Вход:**

* Большой корпус отзывов (разные домены).
* Предобученная модель сентимента по предложениям (NN).
* Морфологический анализатор для лемматизации.

**Что внутри делаем:**

1. **Лемматизируем корпус**

   * режем отзывы на предложения;
   * каждое предложение лемматизируем → список лемм.

2. **Прогоняем предложения через NN**

   * для каждого предложения получаем `sentiment_score ∈ [−1; 1]`.

3. **Собираем статистику по леммам**

   * для каждой леммы `w`:

     * собираем все `sentiment_score` предложений, где она встретилась;
     * считаем среднее → `polarity(w)`;
     * считаем частоту `freq(w)`.

4. **Фильтрация и чистка**

   * отбрасываем леммы с `freq(w) < N_min`;
   * по желанию — выкидываем явно служебные/стоп-слова;
   * делаем быструю ручную проверку:

     * топ-N самых позитивных / негативных / нейтральных;
     * немного подправляем руками (микро-редактирование).

**Выход:**

* Авто-лексикон: `словарь: лемма → polarity(w)`
  (плюс, при желании, частота `freq(w)` для контроля надёжности).

**Глобальная идея:**
Офлайн-часть строит **универсальный оценочный словарь**, используя нейросеть и статистику, чтобы потом онлайн-часть работала с *любым* отзывом без ручного перебора слов.

---

## 2. NLP-обработка конкретного отзыва

**Цель:**
Для *одного* отзыва превратить текст в набор **чётких числовых признаков** (`score_crisp`, интенсивность, неопределённость и т.п.), используя авто-словарь и простые правила.

**Вход:**

* Текст отзыва.
* Авто-словарь `лемма → polarity(w)`.
* Небольшой ручной список:

  * усилителей (`очень, безумно, супер…`),
  * хеджеров/смягчителей (`немного, слегка, скорее, в целом…`),
  * отрицание (`не`).

**Что внутри делаем:**

1. **Нормализация и лемматизация**

   * нижний регистр, очистка;
   * токенизация + лемматизация → последовательность лемм.

2. **Поиск в словаре**

   * для каждой леммы проверяем:

     * есть ли `polarity(w)` в авто-словаре;
     * является ли она усилителем / хеджером / «не».

3. **Учёт модификаторов на локальном уровне**

   * конструкции вида:

     * `усилитель + оценочное слово` → увеличиваем |polarity|;
     * `смягчитель + оценочное слово` → уменьшаем |polarity|;
     * `не + позитивное` / `не + негативное` → сдвигаем полярность к нулю или слегка меняем знак.

4. **Агрегация в численные фичи**

   * считаем:

     * `pos = Σ polarity(w) для polarity > 0`;
     * `neg = Σ −polarity(w) для polarity < 0`;
   * **главный скор**:
     [
     score_crisp = \frac{pos - neg}{pos + neg + 1}
     ]
   * дополнительные:

     * `emotion_intensity_crisp` = Σ |polarity(w)| или среднее;
     * `hedges_count` = количество хеджеров;
     * `coverage` = доля слов, у которых есть `polarity(w)` (покрытие словарём).

**Выход:**

* Набор чисел для отзыва:

  * `score_crisp`, `pos`, `neg`,
  * `emotion_intensity_crisp`,
  * `hedges_count`,
  * `coverage`.

**Глобальная идея:**
NLP-блок — это **мост “текст → числа”**: он берёт отзыв, авто-словарь и простые шаблоны и выдаёт компактный числовой портрет тональности и размытости высказывания.

## Этап 3 — новая корректная формализация

### 3.0. Вход этапа 3

**Вход**: строки из `features.jsonl` (результат этапа 2), минимум:

* `score_crisp`
* `emotion_intensity_crisp` (или ваш финальный “интенсивность эмоций” признак)
* `coverage`
* `hedges_count`
* `pos`, `neg`
* `tokens_alpha` (нужен для нормировок длины)

**Вывод:** этап 3 стартует с чётких признаков из этапа 2, ничего заново “из текста” не считает.

---

### 3.1. Производные признаки (derived features)

Чтобы правила не зависели от длины и ловили “противоречивость”, добавляем:

1. **magnitude** — “сколько вообще сентимента”

Вариант A (если не нормировать):

* `magnitude = pos + neg`

Вариант B (лучше, чтобы не зависеть от длины):

* `magnitude = (pos + neg) / (tokens_alpha + eps)`

2. **conflict** — “насколько смешаны плюс и минус” (высокий, когда pos≈neg)

* `conflict = 1 - abs(pos - neg) / (pos + neg + eps)`

(если `pos+neg` очень мал → конфликт можно считать 0, чтобы “пустые” отзывы не выглядели конфликтными)

3. **hedges_rate** — неопределённость по длине

* `hedges_rate = hedges_count / (tokens_alpha + eps)`

`eps` — маленькое число, чтобы не делить на 0.

**Вывод:** derived-признаки дают системе то, чего нет в одном `score_crisp`: силу/насыщенность и противоречивость, плюс длино-независимую неопределённость.

---

### 3.2. Фаззификация входов

Мы превращаем **каждый входной crisp-признак** в набор термов с μ:

* `score_crisp ∈ [-1; 1]` → термы тональности: {сильно_негативная, негативная, нейтральная, позитивная, сильно_позитивная}
* `emotion_intensity_crisp ∈ [0; 1]` (или другая шкала) → {низкая, средняя, высокая}
* `coverage ∈ [0; 1]` → {низкое, среднее, высокое}
* `hedges_rate ∈ [0; 1]` (или с клипом, например до 0.5) → {мало, средне, много}
* `magnitude ∈ [0; …]` → лучше заранее нормировать в [0;1], затем {низкая, средняя, высокая}
* `conflict ∈ [0;1]` → {низкий, средний, высокий}

Функции принадлежности: треугольники/трапеции (как в примере с водой).

**Вывод:** фаззификация делает из чисел “мягкие слова” (термы), чтобы правила работали плавно, а не порогами.

---

### 3.3. Нечёткий вывод по правилам

Теперь правила **не возвращают те же входы**, а строят **выходные метрики отзыва**.

**Выходные лингвистические переменные (цели этапа 3):**

1. **Итоговая тональность** (`final_tonality`)
2. **Доверие к оценке** (`trust` / `reliability`)
3. **Итоговая интенсивность эмоций** (`final_emotion_intensity`)
4. **Сила впечатления** (`impression_strength`)

**Что делают правила (примеры, без полного списка):**

* Пример про доверие:
  “ЕСЛИ `coverage` низкое ИЛИ `hedges_rate` много → доверие низкое”
* Пример про корректировку тональности:
  “ЕСЛИ `score_crisp` позитивная, НО `coverage` низкое → итоговая тональность слабопозитивная”
* Пример про силу впечатления:
  “ЕСЛИ `magnitude` высокая И `conflict` высокий → сила впечатления высокая (даже если знак тональности около нейтрали)”
* Пример про эмоции:
  “ЕСЛИ `emotion_intensity` высокая И `magnitude` высокая → итоговая интенсивность высокая”

Технически: считаем “силу срабатывания” правила через AND (обычно min/произведение), объединяем вклады по каждому выходному терму через max/сумму (в зависимости от выбранной схемы).

**Вывод:** правила — это место, где появляются **новые смысловые оценки** (final/trust/strength), а не повтор входных чисел.

---

### 3.4. Агрегация по каждому выходу

Для каждого из 4 выходов после всех правил мы получаем **нечёткое множество** (μ по термам выхода), например:

* итоговая тональность: {нейтральная 0.4, слабопозитивная 0.6}
* доверие: {низкое 0.7, среднее 0.3}

**Вывод:** после вывода у нас “распределение по словам”, а не одно число.

---

### 3.5. Дефаззификация (получить числа)

Теперь переводим выходные множества в **чёткие значения**:

* `final_tonality_crisp` (например, в диапазоне [-1;1])
* `trust ∈ [0;1]`
* `final_emotion_intensity ∈ [0;1]`
* `impression_strength ∈ [0;1]` (или 0..100 — как решите)

Методы:

* **Centroid (центр тяжести)** — классика для Мамдани (если выход задан треугольниками/трапециями).
* Либо **Sugeno** (если вы задаёте выходы константами/линейными функциями) — часто проще, но это уже выбор модели.

**Вывод:** дефаззификация — это “из мягких термов” получить финальные численные метрики для отчёта/сортировки/графиков.
